# Waiting on you

Use `ask_owner` when work needs the owner's judgement. It posts one card in the
requesting agent's Discord home channel and records it in the deployment data
directory's `owner-asks.db`. The call returns immediately. The owner can answer
on the card, and the engine gives the agent a continuation in that same channel.
Existing HITL tool approvals keep their existing behaviour and are not included
in this waiting list. An answer here does not bypass a required tool approval.

```python
ask_owner(
    question="Publish the reviewed draft?",
    default="Keep the draft unpublished until you answer.",
    context="The reviewed file and its preview are linked in the preceding message.",
    request_key="draft-review-17",
)
```

`question` and `default` are required. The default must name the consequence of
silence, not merely ask for an acknowledgement. It is always visible on the card.
The engine never executes that default or converts silence into approval.
Only ask when a decision matters. Ordinary status updates belong in chat.

Without `options`, the bot seeds ✅ for yes and 🔴 for no. An optional list of
two to five distinct labels supplies persistent buttons instead. A reply must
use Discord's Reply on the exact card; an unrelated message in the channel
cannot accidentally answer it. Replies may contain a choice or another answer,
up to 400 characters. Longer or empty replies are marked ⚠️ and leave the ask
open. The card states that only recipient replies up to 400 characters are
passed on. Other users' replies, overlong replies, and replies to closed cards
are not passed to the agent; use an ordinary channel message to talk to it. A
reply is recorded verbatim, not interpreted as a yes by a model.

Only the recorded recipient may answer. The checks bind the original bot
account and author, message, channel and guild. Buttons additionally bind the
current revision. Bot actions, other users and old controls cannot approve.
Unrelated interactions with a known card never reach the generic approval
reaction handler. Other users clicking a button receive a private refusal.
Closed cards are edited in place and their buttons are disabled. If adding
reactions fails, the same card explains the reply fallback. Without Embed Links,
the same card uses plain text. No mentions are generated by ask text.

Keep the question within 400 characters, default within 300, context within
400, each option within 50, and their combined text within 1100. These limits
also leave room for an answer in the plain-text fallback. Limits count Discord's
UTF-16 character units. No answer is silently truncated.

`request_key` is an optional stable identifier for one decision. Retrying the
same key and unchanged content returns the existing request, even after it is
answered. Reusing a key for different content is refused. Without a key,
identical concurrent open asks are deduplicated, but an identical later decision
can create a new ask. Use a key when retrying after a tool timeout.

## The waiting list and notifications

`/pending` is private. The configured owner sees every open ask; another user
sees only asks addressed to their Discord ID. Requests are grouped by agent,
with the newest group and request first, ages and links to the exact cards.
The report uses a fenced list with numbered, tappable jump links directly below
it, never a Markdown table. URLs inside a code block would not be tappable.
A report that exceeds
Discord's message limit is attached in full to one private reply or DM.
No rows are dropped to fit. Terminal agent-notification failures appear in a
separate section, with the same privacy filter and a jump link. These records
are closed decisions, not open requests for another answer.

One morning DM contains the same list, only when something is open. No empty
DM is sent or reserved. If the engine starts after the configured hour, it sends
that day's first nonempty list when a bot is available. It does not replay prior
days. The configured timezone governs the day, including clock changes.

An open ask gets one reminder after four hours by default. At seven days it
becomes stale, the card is edited, and the agent receives an expiry event with
no answer and no approving user. Expiry is checked before reminders and digests,
and also when the owner tries to answer an expired card.

```yaml
waiting_on_you:
  enabled: true
  owner_id: ""           # infer only when admin_users.discord contains one ID
  digest_hour: 8         # 0..23, in the timezone below
  timezone: UTC         # an IANA timezone
  remind_after: 14400    # seconds, one reminder attempt
  stale_after: 604800    # seconds, must exceed remind_after
```

An explicit `owner_id` must be in `admin_users.discord`. Multiple configured
admins require an explicit owner; an arbitrary admin cannot answer a card
addressed to someone else. Existing asks stay addressed to their original
recipient. Settings apply after restart; new timing values affect new asks.
Turning the feature off pauses maintenance and creation, and preserves records.
Recorded answers resume delivery when it is enabled again.

Agents with explicit tool allowlists need `ask_owner` allowed by their existing
policy. Use it instead of ordinary untracked approval posts. The engine does not
scrape or import old channel messages. It does not change any tool permissions.
The agent must resolve to a Discord home channel and bot account; existing
home-channel resolution applies. Application-alert channels are reserved.

## Delivery and restart behaviour

Creation intent is committed before posting; the message ID is committed before
controls are enabled. A stable nonce requests Discord's duplicate-send protection
for SDK retries. If acknowledgement is lost, the engine can recover one matching
original-bot card among the latest 100 channel messages. The complete initial
card must match, including an invisible recovery marker. Uncertain sends are
never blindly repeated. If recovery cannot confirm a card, `/pending` retains
the ask with delivery shown as unconfirmed until it expires. A restart can try
that bounded recovery again. An operator must investigate an unresolved send;
reposting a second request could create two decisions.

Answer and expiry transitions commit atomically with a continuation event.
Card edits retry without reposting. Agent continuations survive restart and
serialize through the normal agent session. They are excluded from the generic
restart prompt queue so recovery does not create a second continuation.
An interrupted continuation can be
replayed with the same event ID, so the agent is explicitly told to inspect
prior work before repeating actions. This is durable delivery, not a promise of
exactly-once external actions by a model. An event is marked delivered only
after an explicit successful manager receipt,
including a successful provider turn that chooses `NO_REPLY`. Silent admission
refusals and provider error/auth/usage-limit/timeout/aborted results are not
delivery receipts.

An expiry is an engine notification to its own agent, not a human message.
Only the actual notification object currently issued by this service can pass
sender messaging admission for that agent. A matching user ID or ask ID in an
ordinary incoming message cannot do so. This grants no sender tool privileges,
does not impersonate the owner, and does not reset or bypass a goal's turn
budget. The existing HITL gates still govern gated tools.

Transient delivery failures have at most three attempts, with 60 seconds then
300 seconds between attempts and a 30-minute bound per attempt, including time
queued behind another turn. Attempts and delays persist through restarts. A
known permanent refusal, such as an exhausted goal budget, missing agent or
revoked sender access, stops immediately. An aborted provider turn also stops
immediately, preserving a deliberate stop or approval refusal. Failed delivery changes the same card
to an amber notification failure, stays visible in `/pending`, and logs an
error. It does not send extra DMs or reopen the decision. The owner can contact
the agent directly; no automatic retry occurs after the cap. Card edit failure
retains the dirty edit for retry; the `/pending` failure remains available.

The migration adds columns to existing tables without changing old asks,
answers or message bindings. An uncertain V1 card can still be recovered in its
original format and receives the new reply notice on its next edit. Historical
V1 events already marked delivered are retained; their actual delivery cannot
be reconstructed retroactively.

Reminder and digest intent is committed before sending, with a stable nonce for
SDK retries. Each ask has at most one reminder send attempt, and each recipient
has at most one digest attempt per local date. A closed DM or an uncertain
network result does not cause repeated notices. Delivery status remains
`sent`, `failed` or `uncertain` locally; a process death between committing intent
and sending can lose that notice. `/pending` remains available. This deliberately
favours avoiding duplicate reminders over blind resends after uncertainty.

The database is mode `0600` and uses WAL. It belongs with the other deployment
SQLite stores and their backup. This is a single-engine worker, like the rest of
the platform. This change supplies no live configuration and sends no live ask.
